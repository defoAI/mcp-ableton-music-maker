Design notes for review

The app taps the audio Live sends to the speakers, on this Mac, through macOS's own process-tap API, and draws it. Nothing is routed, no virtual device is installed, and Live keeps playing through whatever output it had. The audio exists only in memory for the length of one analysis window and is never written, kept or sent. Only Live's process is tapped: not the microphone, not the browser, not the system.

Decisions taken in this prototype
  • Tap Live's process, not the system. Spotify in the background never shows up, and the permission asked for is the narrowest macOS offers.
  • Artist units. dBFS with 0 at the top, like Live's own meters; a log frequency axis with the ranges named the way people talk about a mix: sub, bass, low mids, mids, presence, air.
  • The scope is the screen. One spectrum, the master meters beside it, the words under it. No per-track lanes here: a tap hears the mix only.
  • Listening is visible. A pulsing LED in the sidebar and the menu bar while the tap runs; closing the window or leaving the screen stops it.
  • A float window. A small always-on-top copy so the spectrum can sit beside Live's window during a session.
  • Runs on the Mac you have. The app still opens on macOS 12 and 13; the Listen screen explains what it needs there instead of the app refusing to launch.
What the app has to grow
  • A tap module in the Rust core: find Live's process, create the tap and a private aggregate device, read blocks on the audio thread into a ring buffer.
  • An analysis thread at ~30 frames a second: FFT, log-spaced bands in dB, peak and RMS per channel, correlation, peak hold. One small event per frame to the window.
  • The permission string in the bundle's Info.plist and a signed build, or macOS never shows the prompt.
  • The three tap symbols loaded at runtime so the binary still launches on macOS 12 and 13.
  • The server crate is untouched. Claude does not see this screen.
Questions for the review
  1. Tap Live only, or the whole system? Proposed: Live only.
  2. Should Claude get these numbers? Proposed: not in this story. Captures already give Claude a measured mix; a live feed would make the app a data source for the server, which is a new architecture.
  3. Should the six range names join the sound vocabulary so "more sub" and "less low mids" work in shape_sound? Proposed: a separate story; today the vocabulary is parameter words (cutoff, drive, reverb …).
  4. Minimum macOS. Proposed: keep 12 for the app, gate the screen at 14.4.
  5. Float window in the first release? Proposed: yes, it is what makes the screen useful during a session.
  6. Scope view (waveform) too? Proposed: later, as a second view on the same screen.
  7. Per-track meters from the Remote Script beside the spectrum? Proposed: a separate story; that data comes over the Live socket, not the tap.
