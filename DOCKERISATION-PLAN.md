# Dockerising ableton-mcp

**Repo:** `ableton-mcp/` (clone of github.com/ahujasid/ableton-mcp, commit 8731a47, 30 August 2026, v1.4.0)
**Written:** 2026-09-19
**Status:** implemented 2026-09-19 for the Python server, then superseded the same day by the Rust port: the image now builds the `ableton-mcp` crate (see `Dockerfile`, `CLAUDE.md`). Sections below describe the Python-era image and are kept for the reasoning; file paths and commands in them no longer exist. Sections 4 and 5 below are annotated with what was
actually done and the verification results from a Linux/arm64 Docker engine. Items that need
a Mac with Live open are marked **pending on Mac**. See section 7 for decisions that differ
from the plan.

## 1. What can and cannot be containerised

The project is two processes:

| Process | Where it must run | Why |
|---|---|---|
| `AbletonMCP_Remote_Script/__init__.py` | Inside Ableton Live on the Mac | It is a Live control surface. Live loads it from the User Library. No container can do this. |
| `MCP_Server/server.py` | Anywhere that can reach TCP 9877 on the Mac | Plain Python, talks to Live over a socket and to the MCP client over stdio. |

So "properly dockerised" means: the MCP server runs in a container that the MCP client
(Claude Desktop, Claude Code, Cursor) launches over stdio, the container reaches Live on the
host, and nothing else leaves the container. The remote script keeps being installed on the
host by the existing `ableton-mcp-install-script` command, which we also run from the image
with the Ableton folder mounted.

## 2. What the current Dockerfile gets wrong

The shipped `Dockerfile` was generated by Smithery and is not fit for local use:

- `python:3.10-alpine` plus `gcc musl-dev libffi-dev`: builds C extensions at image build
  time on musl, slow and fragile. The project's own `.python-version` says 3.13.
- `COPY . /app` before `pip install .`: every source edit invalidates the dependency layer,
  and the copy includes `.git`, `tests/`, `uv.lock` and anything gitignored that exists
  locally, including a `MCP_Server/config.py` with Supabase credentials if one is present.
- `pip install .` ignores `uv.lock`, so the image is not reproducible.
- Runs as root, no `HEALTHCHECK`, no `.dockerignore`, no way to pass the Live host.
- Nothing about the telemetry and dataset switches, which we want hard-off in the image.

## 4. Steps

### 4.1 Dockerfile: multi-stage, uv, locked, non-root

- Base `python:3.13-slim-bookworm`. All dependencies in `uv.lock` (73 packages, `mcp`,
  `supabase`, `httpx`, `pydantic`) ship wheels for manylinux, so no compiler is needed.
- Stage 1 (`builder`): copy `pyproject.toml` and `uv.lock` only, run
  `uv sync --frozen --no-dev --no-install-project` so the dependency layer caches. Then copy
  `MCP_Server/` and run `uv sync --frozen --no-dev` to install the project itself.
- Stage 2 (`runtime`): copy `/app/.venv` from the builder, create user `mcp` (uid 1000),
  `USER mcp`, `WORKDIR /app`.
- `ENV` defaults baked in: `ABLETON_HOST=host.docker.internal`, `ABLETON_PORT=9877`,
  `ABLETON_MCP_DISABLE_TELEMETRY=true`, `ABLETON_MCP_DISABLE_DATASET=true`,
  `ABLETON_MCP_STATE_DIR=/state`, `PYTHONUNBUFFERED=1`.
- `ENTRYPOINT ["/app/docker/entrypoint.sh"]`, `CMD ["ableton-mcp"]`.
- `.dockerignore`: `.git`, `.venv`, `tests`, `*.md`, `smithery.yaml`, `.github`,
  `MCP_Server/config.py`, `.env*`, `__pycache__`. The `config.py` line is the important
  one: it is the only thing that could make the image phone home.
- Pin the `uv` copy stage to a digest (`ghcr.io/astral-sh/uv:0.x@sha256:…`), not `latest`.

Reference: 3.13 matches `.python-version`. `requires-python` says `>=3.10`, so 3.13 is
within range. The README's "Python 3.8" is stale.

### 4.2 Entrypoint

`docker/entrypoint.sh` does three things and then `exec "$@"`:

1. `mkdir -p "$ABLETON_MCP_STATE_DIR"` and check it is writable, so a missing volume
   fails loudly instead of silently re-asking for consent each run.
2. If `ABLETON_MCP_DISABLE_DATASET` is anything other than a true value, print a one-line
   warning to stderr. stderr is safe: MCP uses stdout for the protocol.
3. Point `HOME` at `/state` so `telemetry.py`, which ignores `ABLETON_MCP_STATE_DIR` and
   writes `customer_uuid.txt` under `~/.local/share/AbletonMCP`, lands in the volume too.

Do not print anything to stdout in the entrypoint. A single stray line breaks the MCP
handshake.

### 4.3 docker-compose.yml

One service, `ableton-mcp`, for building and for running the installer and tests. Not for
the MCP client itself, which launches `docker run` directly (4.5).

```yaml
services:
  ableton-mcp:
    build: .
    image: ableton-mcp:local
    stdin_open: true
    tty: false
    environment:
      ABLETON_HOST: host.docker.internal
    extra_hosts:
      - "host.docker.internal:host-gateway"   # no-op on Docker Desktop, needed on Linux
    volumes:
      - ableton-mcp-state:/state
    read_only: true
    tmpfs: [/tmp]
    security_opt: [no-new-privileges:true]
    cap_drop: [ALL]
volumes:
  ableton-mcp-state:
```

`read_only: true` plus the `/state` volume is the point: the container cannot write
anywhere else.

### 4.4 The Ableton side

- The remote script binds `0.0.0.0:9877` (line 20 of the script). Change `HOST` to
  `127.0.0.1` and verify the container still reaches it through `host.docker.internal`.
  On Docker Desktop for Mac the host-gateway proxy connects from the host's own loopback,
  so this should work; it is the first thing to test (section 5). If it does not, keep
  `0.0.0.0` and rely on the macOS application firewall.
- Installing the script from the image: run `ableton-mcp-install-script` with the Live
  User Library mounted, for example
  `docker compose run --rm -v "$HOME/Music/Ableton/User Library:/lib" ableton-mcp ableton-mcp-install-script --target "/lib/Remote Scripts"`.
  The installer only copies a file and makes a `.bak`, so a bind mount is sufficient.
  Check `--dry-run`-style output first: the installer has a flag that lists discovered
  directories without writing (`remote_script_install.py`, around line 286).
- Live must be restarted after the script changes. Document that.

### 4.5 Client configuration

Claude Desktop / Claude Code config, replacing the `uvx` entry:

```json
{
  "mcpServers": {
    "AbletonMCP": {
      "command": "docker",
      "args": ["run", "--rm", "-i",
               "--read-only", "--tmpfs", "/tmp",
               "--security-opt", "no-new-privileges:true", "--cap-drop", "ALL",
               "-v", "ableton-mcp-state:/state",
               "ableton-mcp:local"]
    }
  }
}
```

`-i` keeps stdin open for stdio. No `-t`. No `-p`: the container makes an outbound
connection to the host and exposes nothing. Docker Desktop must be running before the
client starts, which is the main usability cost of this approach; note it in the README.

### 4.6 Tests in the image

`tests/test_clip_notes.py` mocks the socket, so it runs anywhere. Add a `test` stage or
a compose profile that installs dev deps (`uv sync --frozen --group dev` after adding
`pytest` to a dev group in `pyproject.toml`) and runs `pytest -v`. Keep tests out of the
runtime image.

### 4.7 CI

GitHub Actions on push: build the image, run the tests in it, then run three assertions on
the runtime image:

1. `docker run --rm ableton-mcp:local python -c "import MCP_Server.config"` must fail
   with `ImportError`. This proves no credentials shipped.
2. `docker run --rm ableton-mcp:local id -u` prints `1000`.
3. A `docker scout cves` or `trivy image` scan with a failure threshold on critical CVEs.

Optionally push to GHCR tagged by commit, so `docker run ghcr.io/<you>/ableton-mcp:<sha>`
replaces the local build in 4.5.

### 4.8 Network egress (decide, do not assume)

With `config.py` absent the code has no outbound destination except Live. Two ways to
make that a guarantee rather than a fact about the current version:

- **Option A, internal network.** `networks: {mcp: {internal: true}}` blocks all egress
  but on Docker Desktop also blocks `host.docker.internal`, so it does not work here.
- **Option B, verify not restrict.** Keep the default network and rely on the CI assertion
  in 4.7 plus the two disable variables. Add a test that starts the server with a fake
  `config.py` containing credentials, points `ABLETON_HOST` at a mock, and asserts no
  connection is attempted to the Supabase URL while the disable variables are set.

Recommendation: B. It is checkable and does not fight Docker Desktop's networking.

## 5. Verification checklist

Run in this order on the Mac, with Live open and the script installed:

- [x] `docker compose build` completes without a compiler in the image
      (`docker/verify-image.sh` asserts no `gcc`, `cc` or `uv` binary).
- [x] `docker run --rm ableton-mcp:local python -c "import MCP_Server.config"` raises
      `ModuleNotFoundError` (verify-image.sh check 2).
- [ ] **pending on Mac:** `HOST` in the remote script was left at `0.0.0.0` (section 7).
      Reachability test to run once on the Mac:
      `docker run --rm ableton-mcp:local python -c "import socket; socket.create_connection(('host.docker.internal', 9877), 3)"`.
- [ ] **pending on Mac:** Claude Desktop lists the AbletonMCP tools and `get_session_info`
      returns the open set. The stdio handshake itself is verified: an `initialize` request
      piped into the container returns `serverInfo` for `AbletonMCP` with Live absent, and
      every stdout line is JSON-RPC (verify-image.sh check 6).
- [x] Runtime user is uid 1000 and `--read-only` is honoured (checks 3 and 8); compose sets
      `read_only`, `cap_drop: [ALL]`, `no-new-privileges`.
- [x] The consent question is never shown: `needs_prompt()` is `False` and
      `consent_state()` is `denied` under the image environment (check 5). `/state` stays
      empty with the image defaults; a named volume is writable by uid 1000.
- [x] `docker compose --profile test run --rm --build test`: 23 passed.
- [x] Image size 73 MB (check 7, limit 200 MB).
- [x] `docker compose --profile install run --rm install-script` against a temporary User
      Library writes `Remote Scripts/AbletonMCP/__init__.py` (script_version 1.7.0).
- [x] Smithery's `python -m MCP_Server.server` command still completes the handshake.

## 6. Open questions

1. **Keep `uvx` as a documented alternative?** Simpler for users without Docker. If yes,
   the README must say that path is unsandboxed and must show both disable variables.
2. **Strip the telemetry and dataset packages entirely** in this fork, rather than
   disabling them? It removes `supabase` and about 40 transitive packages from the image
   and removes the whole class of risk. Cost: merges from upstream get harder. Worth a
   separate decision once the Docker work is done.
3. **Linux hosts.** Live does not run on Linux, so `host.docker.internal` via
   `host-gateway` only matters for a Mac running the server in a remote Linux Docker
   engine. Out of scope unless needed.

## 7. Decisions made during implementation

1. **All telemetry is now opt-in in the code, not only in the image.** Requested by the
   maintainer on 2026-09-19 ("disable all telemetry by default"). The anonymous tier needs
   `ABLETON_MCP_ENABLE_TELEMETRY=true`; dataset recording needs telemetry on plus an explicit
   yes (`recording_allowed()` now returns true only for `GRANTED`, never for `UNKNOWN`), or
   `ABLETON_MCP_ENABLE_DATASET`. Disable variables still override everything. With telemetry
   off the consent question is not asked at all, since a yes could not start anything.
   `TERMS.md` and the README were rewritten to match, and `tests/test_privacy_defaults.py`
   pins the behaviour with a fake `config.py` that carries credentials and a stubbed Supabase
   client factory. This also resolves open question 6.2 for now: the packages stay, the
   defaults make them inert. Section 4.8 option B is implemented by those tests.
2. **Remote script `HOST` stays `0.0.0.0`.** Changing it to `127.0.0.1` cannot be verified
   without a Mac running Live and Docker Desktop, and a wrong guess breaks the only path into
   Live. Test it on the Mac (section 5) and change it in a separate commit if it works.
3. **Entrypoint warns rather than fails on an unwritable state dir when both tiers are
   off**, because in that state nothing is ever written. It exits 1 only if telemetry or
   dataset recording is enabled and `/state` is not writable. In practice the `VOLUME /state`
   declaration makes Docker mount an anonymous volume there on every run, so the path is
   writable even under `--read-only`; the error branch only fires for a read-only bind mount.
4. **Telemetry writes go to `/state` via `XDG_DATA_HOME`**, which `telemetry.py` honours on
   Linux, instead of relying only on `HOME`. `HOME` is also set to `/state` as a backstop.
5. **The test stage runs `pytest -p no:cacheprovider`** so the suite passes on a read-only
   root with `--network none`.
6. **`.mcp.json` and `CLAUDE.md` were added** so Claude Code offers the containerised server
   when the repo is opened and knows the repo's invariants (stdout purity, opt-in telemetry,
   no `config.py`, image contract).
7. **compose `run` replaces the installer's command**, so `--list-targets` cannot be appended
   to the `install-script` service; it is also meaningless inside the container. The service
   always installs into the bind-mounted `/user-library/Remote Scripts`.
8. **`uv.lock` was regenerated** (uv 0.12.17, lock revision 3) to add the `dev` group with
   pytest. Only pytest and its three dependencies were added; no existing pin changed.
