Design notes

    

      

        
What the screen is for

        
    
          
  • A producer who has just finished Setup has the tools connected and no idea what to say. The client shows a list of 105 tools; the server's instructions are handed to the model, not to the person. This screen is the person's half.
    • 
          
  • Every prompt is finished text. No fields to fill in: copy, paste, and Claude runs the interview in chat where the producer can answer loosely ("something like Burial but faster").
    • 
          
  • Each prompt carries three things the producer would never think to write: the order of operations (key before notes, dry_run before build, capture_mix before claiming it sounds right), the rules Live imposes (launch on the bar, Cmd+S is the producer's, a fresh set sits in C Major), and how to talk (two lines per move, play it, ask keep-or-change).
    • 
          
  • The four cards are the four states a producer is actually in when they open the app: nothing yet, a pile of half-finished material, one sample they love, or a gig tonight.
    • 
          
  • Two of them are loops, not recipes. Make a song does not stop at a built set: it plays each section back, changes what the producer reacts to, measures again, asks again — and is told never to call the mix finished. Prepare a set spends most of its text on what happens while the music runs: build the next section out of the one looping now, queue it ahead of the playhead, and never touch a clip that is sounding this phrase.
    • 
        

      

      

        
Decisions taken into this mock

        
    
          
  • Static text, Claude asks. The app never asks for genre, BPM or length — the prompt tells Claude to ask, with a default offered for each so the producer can just say "go".
    • 
          
  • One markdown file per prompt in the repo, embedded in the app at build time. A PR can review the wording; a Claude Code or Cursor user reads the same file without the Mac app.
    • 
          
  • The screen knows the state of the chain. Copy still works when Live is closed — the producer may be preparing on the train — but the banner says what will fail and links to Setup instead of letting Claude find out.
    • 
          
  • Copy is the only action. No "send to Claude" button: the server is started by the client, the app never holds the conversation. Pretending otherwise would be the one dishonest control on the screen.
    • 
          
  • Every tool name in the text is a real one, spelled as the model will see it (capture_mix, adv_keep_track_playing). A prompt that names a tool that does not exist is worse than no prompt.

Open questions for this review

    

      

        1. Does the performance prompt belong on this screen at all, or on the Overview when a song exists?
        
Preparing a set is the one thing a producer does after they have material. A card that is useless on day one may be better surfaced where the app already knows there are sections.

      

      

        2. Should a copied prompt show up in Activity?
        
The app would be recording something the producer did in the app, not a tool call. Leaning no: the activity log is the record of what reached Live, and widening it needs a TERMS.md line.

      

      

        3. Do the prompts name the client?
        
"Paste into Claude Desktop" is clearer, but the same text is pasted into Claude Code and Cursor. Currently the text names no client and the screen says "into Claude".

      

      

        4. How does a prompt stay true when a tool changes?
        
These name real tools and real workflow. If feel gains a mode or play_song changes its record question, the prompt is stale and nothing fails. Proposal: a test that every tool name in prompts/*.md exists in the server's tool list.
